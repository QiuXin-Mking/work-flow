# 相似工作流框架调研

核对日期：2026-10-29。范围是本项目最新目标流程，不是单纯比较模型修 Bug 跑分。资料仅采用项目官方 GitHub 与官方文档；本轮没有安装、跑通或验证任何候选。

## 1. 结论

有相似框架，而且一些项目已覆盖“研究后规划、用户参与、隔离执行、PR 交付”的主要部分。本轮未找到官方资料可证明原生实现本项目完整业务契约的单一框架。

优先深入三个方向：

1. **HumanLayer**：流程和团队工作台最相似，可借鉴 Questions → Research → PRD → 实施 → PR。
2. **GitHub Spec Kit**：最值得验证能否承载显式门槛、循环收敛、暂停恢复，且可按扩展定制。
3. **OpenHands Agent Canvas**：最值得比较远程执行控制面、已有 Web 界面及不同 coding agent 的切换。

这些是不同替换层次：HumanLayer/Canvas 更接近整个平台；Spec Kit 更接近流程机制。不要把三套全部叠入，也不要把选择 coding runner 当作已解决业务状态机。

## 2. 与本项目的匹配标准

目标链路：独立工单快照 → 信息足够性诊断 → 74 环境日志/trace-id 和代码根因 → 用户确认关键业务行为 → PRD 讨论及双重收敛 → worktree → 修前失败/修后通过 → 人工审核 → 两仓 PR。

Feishu、自有 mobi 语义、74 SSH 取证规则、Trellis spec 索引、同版 PRD 双审和多仓候选审批绑定，是企业业务契约。支持“自定义工具”或“子 Agent”不能证明这些契约已经实现。

表中“可定制”仅表示有机制可承载，不表示开箱满足。

| 框架 | 官方已有能力 | 本项目主要补充 | 最适合承担的层 |
| --- | --- | --- | --- |
| HumanLayer | Questions/Research/PRD 等阶段、团队任务/会话、远程 daemon、多 coding agent | 飞书入口、业务信息规则、74 证据门槛、双审绑定、两仓交付一致性 | 完整工作台或流程参考 |
| Spec Kit | Bug fixing 扩展、可组合 workflow、gate、条件循环、持久化暂停恢复 | 自有业务步骤、Web 决策界面、SSH/沙箱、审批身份及产物版本 | 显式流程引擎 |
| OpenHands Agent Canvas | Web 控制台、远程/容器后端、第三方 agent、issue-to-PR automation | PRD 前硬门槛、三项业务确认、双审循环、多仓事务边界 | 执行平台与 UI |
| Agent Orchestrator | Agent/branch/worktree 隔离、会话看板、CI/Review 反馈、Claude Code 等 runner | 需求入口和根因门槛、PRD 收敛前禁止建修改工作区 | 工作区与 PR 执行管理 |
| GSD Core | Discuss/Plan/Execute/Verify/Ship、新上下文子 Agent、文件化状态 | 服务端硬门槛、团队权限、74/飞书、版本审批、多仓发布 | 流程技能与上下文管理 |
| LangGraph | Checkpoint、interrupt、resume 等运行机制 | 几乎全部领域流程、工具、worktree、UI 和 PR 交付 | 保留现有系统时的底层编排 |

证据入口分别见下面各节；“缺失”表示本轮官方资料未证实原生具备，不是断言技术上无法扩展。

## 3. HumanLayer：最接近业务讨论与规划链

官方工作流列出 RPI 和 PRD-Oriented 两种路径；后者包含 Questions、Research、PRD、TDD、结构、实施和 PR，并提供 create/iterate 产物命令。该阶段设计与本项目“先补信息和研究，再收敛文档”的方向接近。[官方技能与流程表](https://docs.humanlayer.com/reference/skills-workflows)、[阶段解释](https://docs.humanlayer.com/explanation/workflow-phases)

它还包含 Web/桌面入口、主机 daemon，以及 Claude Code、Codex、OpenCode、Pi 接入。源码是多应用 monorepo；官方明确自托管指南仍在完善中，不应将其评为“一键替换42”。[官方仓库 README](https://github.com/humanlayer/humanlayer#readme)

**可复用：** 团队任务、远程执行和分阶段产物交互。**需补：** 信息不足必须停止的业务规则、74 日志因果证据、PRD 同版双重判断、审批内容哈希及两个仓库的原子业务边界。官方流程名称相似，不等于已提供这些强校验。

**采用成本：中高。** 借鉴流程技能成本较低；整个平台替换涉及 daemon、数据库/同步和账号部署，需验证42适配。替换 Pi 为 Claude Code 在其支持范围内，但本项目工具、规范及状态适配仍需实现。

## 4. Spec Kit：显式流程和门槛值得优先验证

官方现有独立 Bug fixing 入口，以根因评估、限定修复及验证为结果；扩展和 preset 可以定制流程与规则。它不只是一套“先写 spec”的模板。[官方 README 的 Choose your process / Capabilities](https://github.com/github/spec-kit#readme)

workflow 文档明确支持 gate、条件/循环、fan-out/fan-in，保存 run state 和日志，并可恢复 paused/failed 执行。gate 可以绑定外部输入，适合由前端确认后恢复；但沙箱不是它提供的能力。[官方 Workflow：State and Resume、Gate Verdict Inputs、Security note](https://github.github.io/spec-kit/reference/workflows.html)

**可复用：** 把信息诊断、根因、用户确认及两次收敛检查作为独立节点；这是适配推断，不是官方已有企业 Bug 流程。**需补：** 各节点的 JSON/schema 和证据判断、用户身份、Web 适配、SSH、独立工作区及发布校验。尤其不能将 shell step 当成权限沙箱。

**采用成本：中。** 可保留现有飞书和 Web 外壳，先验证一条“暂停→前端确认→恢复”链路。它仍需 coding-agent integration；Claude Code 接入应按固定版本的集成矩阵与无头调用实测，不等于直接复用 Pi RPC。

## 5. OpenHands Agent Canvas：远程执行与界面更完整

当前官方仓库主入口为 Agent Canvas，可连接本地、远程和云后端，支持 OpenHands、Claude Code、Pi 等 agent/ACP 接入。[官方仓库 README](https://github.com/OpenHands/OpenHands#readme)、[官方后端文档](https://docs.openhands.dev/openhands/usage/agent-canvas/backends)

它已有 issue-to-PR automation，适合比较事件入口和执行控制，但该自动化不能证明已满足“根因明确以后才能出 PRD”及本项目的用户确认契约。[官方 Issue to Pull Request Automation](https://docs.openhands.dev/openhands/usage/agent-canvas/prebuilt/issue-to-pr)

**可复用：** Web 控制面、后端连接、隔离运行能力。**需补：** 飞书适配和门槛流程、同版 PRD 双审、74 取证规范、多仓候选绑定。**采用成本：中高。** 先对比远程部署与 ACP 结束协议；不同后端的会话恢复、容器、权限能力需要单独验收，不因产品有暂停交互就假定持久执行满足要求。

## 6. 其他候选的定位

### Agent Orchestrator

原 ComposioHQ 地址现跳转到 OrchestratorInc。官方描述每项任务分配 agent、branch 和 worktree，集中会话状态，并将 CI/Review 反馈回负责 worker；支持 Claude Code 等执行器。[官方仓库](https://github.com/OrchestratorInc/agent-orchestrator#readme)

适合参考代码执行后的隔离和反馈循环。它的工作区建立时机需调整，本项目要求 PRD 双审后才能创建修改工作区。整套改造成本中高；不能从多任务、多项目能力推导出同一业务事务的两仓 PR 审批绑定。

### GSD Core

旧 gsd-build/get-shit-done 仓库已归档，官方 README 指向 open-gsd/gsd-core。新项目围绕 Discuss、Plan、Execute、Verify、Ship，使用新上下文子 Agent 和文件化状态，支持 Claude Code 等多运行时。[旧仓库迁移说明](https://github.com/gsd-build/get-shit-done#readme)、[现官方仓库](https://github.com/open-gsd/gsd-core#readme)

适合借鉴收敛讨论和子 Agent 上下文。技能遵循不等于服务端硬阻断；作为42常驻流程引擎仍需补状态、权限、错误恢复及业务规则。技能采用成本较低，平台化成本较高。

### LangGraph

适合已经决定保留工作台，只替换底层协调机制的情况。interrupt 保存状态并等待外部输入，使用持久 checkpointer 和 thread_id 恢复。恢复会重新执行节点开头，因此中断前副作用必须幂等。[官方 Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[官方仓库](https://github.com/langchain-ai/langgraph)

它不是现成 coding-agent 工作台，不原生提供本项目 PRD/worktree/PR 链路。采用成本高于复用领域流程，但能明确实现门槛；进程超时、SSH及发布仍需自管。不能把 checkpoint 等同于正在运行的外部进程可恢复。

## 8. 对本项目的取舍建议

优先比较 HumanLayer 的业务阶段与交互，再验证 Spec Kit 的门槛运行能力；只有明确需要整体替换控制台/执行后端时，再做 Canvas 的部署比较。Orchestrator 和 GSD 更适合分层参考，不必同时引入。

用于任何候选的最小验收：

1. 缺 mobi 或必要 trace-id 时真正停住，不能仅让模型输出“不足”后继续。
2. 根因未明确时不能生成正式 PRD；用户未确认不能开始修改。
3. 确认和双审绑定同版内容；输入变化后旧批准失效。
4. 进程退出、漏结束事件、服务重启和网络超时均有可解释终态，不能长期显示运行中。
5. PRD 通过后才创建修改 worktree；两个仓库可分析而只改一个。
6. 验证失败不得创建 PR；多仓交付重试不重复或越权发布。

更换 Pi 为 Claude Code 主要改变执行适配层，不能替代以上业务门槛。建议先用固定输入和模拟故障比较协议与恢复，再用一条真实工单评估，避免以安装成功代替架构适配成功。
