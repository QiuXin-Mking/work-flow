# Bug 提单规范

## 1. 适用范围

适用于 `192.168.2.74` 测试环境中 voyager_server 与 operations-dashboard 的缺陷提交，以及 Bug 修复工作台的受理检查。测试人员负责提供可复现、可取证的文字事实；研发与 Agent 负责根据事实定位根因，不代替提单人补写故障表现。

## 2. 文字提单要求

采用纯文字提单，不上传图片或截图，不以“如图”“见截图”“视频里有”“点了没反应”等内容替代实际描述。正文与补充评论执行同一要求。

原本需要截图说明的内容，必须改写为具体文字：

- 页面及入口名称、访问路径，以及实际使用的测试登录账号。
- 操作前的数据状态、选中项和可见内容。
- 依次点击了什么、输入了什么、提交了什么。
- 操作后的实际变化，包含字段值、按钮状态、错误文字或错误码。
- 刷新、重新进入或重复操作后的结果。
- 与期望行为的差异，以及期望依据。

不要粘贴整页 UI 文本或整份日志。错误响应、请求参数和关键日志可使用文字代码块，登录信息必须填写本次复现使用的测试账号和测试密码，不能只写角色名称。请求中的测试会话信息可保留用于复现；与本次复现无关的个人信息、生产凭据和插件密钥不填入工单。

## 3. 必填内容

| 项目 | 填写要求 |
| --- | --- |
| 标题 | 页面/接口 + 操作 + 实际异常，不能只有“功能异常” |
| 故障对象 | 单独填写 `mobi:xxxx`，必须是本次出错对象；不能只填 reportNo 或船名 |
| 环境 | 不填写时默认 `192.168.2.74` 测试环境；涉及客户端时补浏览器/客户端信息 |
| 登录信息 | 实际测试账号和测试密码；多账号切换时逐一列明对应步骤，角色仅作补充 |
| 复现类型 | 明确标注“必现”或“偶现”，不能只填“有时有问题” |
| 前置条件 | 使用哪个测试账号登录、数据状态、相关配置和能定位对象的关联编号 |
| 操作步骤 | 从可找到的入口开始，按顺序列出；同事应能按文字执行 |
| 实际结果 | 明确哪些内容错误、缺失、多出或不生效；有报错必须提供原文 |
| 期望结果 | 明确应该怎样表现，不能只有“正常显示”或“修复即可” |
| 前端组件 outerHTML | 确认涉及前端修改时必填，复制故障相关节点或最小父容器的 outerHTML，并注明页面 URL、用途和对应步骤 |
| 后端请求URL | 判断涉及后端修改时必填，粘贴相关故障请求的完整 cURL (bash)，不能只填 URL；尚不确定时明确注明待定位 |

缺陷等级、经办人、关注人等工单管理字段不能替代上述内容。业务无需提供的个人信息不纳入故障描述。

## 4. 必现与偶现问题

### 必现问题

同样的前置条件和步骤能够稳定触发。建议记录实际重复次数及发生时间，避免把未经重复验证的问题标为必现。有 trace-id 时一并提供；没有时可以先按 mobi 取证。

### 偶现问题

必须已在 `192.168.2.74` 触发，并在工单正文或文字补充中记录对应 `trace-id:xxxx`。同时写明触发条件、实际复现次数/尝试次数和发生时间，说明已在 74 触发。

trace-id 必须对应本次故障请求，不得用其他请求或其他环境的 ID 代替。仅在工作台表单填写 trace-id 而不补入工单，不符合来源追溯要求。

系统不替测试人员自动制造业务请求或测试数据来补足提单条件。

## 5. 描述正例

以下为格式示例，数值和结论仅供说明，提交时必须替换为真实事实。

```text
标题：【清洗报告编辑页】删除左舷后刷新，左舷页签重新出现

mobi:425
环境：192.168.2.74
复现类型：必现
发生时间：2026-10-29 15:20:00
验证次数：同样步骤执行 3 次，出现 3 次

前置条件：
1. 使用测试账号 `<实际测试账号>`、测试密码 `<实际测试密码>` 登录（角色：报告编辑）。
2. 运营配置已选择左舷，未选择右舷。
3. 进入该 mobi 对应的清洗报告编辑页。

操作步骤：
1. 确认页面当前显示“船图”“左舷”两个页签。
2. 点击“左舷”旁的删除按钮并确认。
3. 记录页面提示，再刷新当前页面。

实际结果：
删除后“左舷”页签立即消失，页面提示“删除成功”。
刷新后“左舷”再次出现，运营配置中的左舷选择未发生变化。

期望结果：
若运营配置选择的部位不允许在报告页删除，则不展示删除入口。
期望依据：填写已确认的需求条目或产品文字确认，不依赖截图。

后端请求URL：
判断涉及后端修改时，粘贴对应请求的完整 cURL (bash)。

错误原文/接口结果：
填写真实响应；没有报错时明确写“未显示错误提示”。
```

期望行为尚未得到确认时，明确记录争议和待确认人，不将个人推测写成确定要求。

## 6. 打回条件

出现以下任一情况，不进入根因查询、PRD 或代码修复：

| 原因编号 | 打回原因 | 测试人员应补充或修改 |
| --- | --- | --- |
| BUG-INPUT-01 | 缺少或无法确认故障 mobi | 补写准确 `mobi:xxxx` |
| BUG-INPUT-02 | 图片/截图提单，或依赖“见图”才能理解 | 移除图片，将关键信息完整改为文字 |
| BUG-INPUT-03 | 缺测试账号/密码、前置条件或可执行步骤 | 补到其他人可按文字登录并操作；环境留空按 74 处理，不作为打回理由 |
| BUG-INPUT-04 | 实际结果或期望结果不明确 | 列出具体状态、数值、文字及行为差异 |
| BUG-INPUT-05 | 复现类型不明或复现声明缺乏依据 | 标明必现/偶现，并说明触发情况 |
| BUG-INPUT-06 | 偶现问题未在 74 触发或缺对应 trace-id | 在 74 取证并补入工单 |
| BUG-INPUT-07 | 正文与评论的业务要求冲突 | 澄清并记录明确的文字结论 |
| BUG-INPUT-08 | 工单混入多个互不相关缺陷 | 按独立问题拆单，分别提供证据 |
| BUG-INPUT-09 | 已判断涉及后端修改，但未提供相关请求，或只有 URL | 在“后端请求URL”中补充完整 cURL (bash)；根因阶段确认涉及后端后发现缺失，也须暂停并补齐 |
| BUG-INPUT-10 | 已确认涉及前端修改，但未提供相关 DOM 片段 | 补充 Copy outerHTML、页面 URL、元素用途及对应步骤；后续阶段确认涉及前端时同样暂停补齐 |

打回反馈必须列出原因编号、具体缺失项及修改要求，不能只回复“不符合规范”。测试人员负责按规范重写或重新提单；不要求 Agent 从图片或模糊描述中自行补全。

## 7. 重提与恢复

测试人员修改飞书工单后，由任务发起人使用“重新读取工单”获取新快照，重新进行信息诊断。不能只在聊天中说明已修改就沿用旧快照继续执行。

打回是受理结论，不等于缺陷不存在或已解决。已有历史图片可保留在历史快照中用于审计，但不能成为新一轮受理和后续 Agent 推理的必要输入。

## 9. 后端请求采集步骤

“后端请求URL”字段保存可复现请求的完整 cURL 命令，包含 URL、方法、请求头和请求体。涉及多条相关请求时，按操作顺序分别标注用途并填写，不粘贴整页无关请求。

1. 在 Google Chrome 打开 74 测试页面，使用工单中填写的测试账号和密码登录。
2. 按 `F12` 打开开发者工具，进入 **Network（网络）**。确认左上角录制按钮处于录制状态；如果操作会跳转页面，勾选 **Preserve log（保留日志）**。
3. 点击 **Clear（清除）**，即圆圈内带斜线的图标，清除之前的网络记录；该按钮不是停止录制按钮。
4. 重新执行一次导致故障的操作，让 Network 记录本次请求。
5. 找到与异常操作有关的请求 URL，在该请求行右键，选择 **Copy → Copy as cURL (bash)**，将完整内容粘贴到工单的 **“后端请求URL”** 字段，使用代码块保留格式。
6. 如需采集同一次操作的多条相关请求，可筛选后使用 **Copy all as cURL (bash)**；如果版本菜单仅提供复制单条请求，逐条复制并标注操作顺序。
7. 同时以文字补充请求发生时间、HTTP 状态码和关键响应内容；偶现故障还必须记录对应 trace-id。

复制请求用于故障取证，不代表授权 Agent 自动重放有写入效果的请求。模板中的账号和密码占位符必须在实际提单时替换，不能直接作为有效登录信息提交。

## 10. 前端组件信息采集

确认涉及前端修改时，必须在“前端组件 outerHTML”中提供故障相关元素或区域的 `Copy outerHTML` 内容，并注明页面 URL、元素用途及对应复现步骤。前后端均涉及时，outerHTML 与后端 cURL 均需提供。

1. 在 Google Chrome 登录 74 测试环境，按步骤触发异常，保持故障现场。
2. 按 `F12` 打开开发者工具，进入 **Elements（元素）** 面板。
3. 点击元素选择工具（`Ctrl+Shift+C`），在页面中选择出错的按钮、输入框、页签或照片区域。
4. 在 Elements 中确认选中的节点；涉及多个子元素的布局或分组问题，选择能完整包含故障区域的最小父节点。不要复制整个 `html` 或 `body`。
5. 右键该节点，选择 **Copy → Copy outerHTML**，将结果粘贴到“前端组件 outerHTML”，使用 HTML 代码块保留原文。
6. 多个相关区域分别采集并标注用途；元素缺失时复制其应出现位置的父容器，文字说明缺少哪个元素。

outerHTML 是浏览器渲染后的 DOM 片段，可辅助定位页面，不能当作 React/Vue 源码组件或根因证据，也不能替代复现步骤和实际/期望结果。已确认涉及前端修改但未提供相关 DOM 时，按 **BUG-INPUT-10** 打回补充；如果在根因阶段才确认涉及前端，也在该阶段暂停补齐。

填写格式：

```text
前端组件 outerHTML：
页面 URL：
元素/区域用途：
对应复现步骤：
故障状态说明：
```

随后附 HTML 代码块，粘贴 Copy outerHTML 的完整结果。
