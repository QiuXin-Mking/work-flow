# Trellis 在 Pi Bug 修复工作台中的接入

## 目标与边界

工作台复用 Trellis 一个任务一组持久工件、按职责注入 spec、独立会话交接、检查后沉淀经验的做法。Web 后端持有状态机、租约、仓库集合、证据和人工审核；Pi 只执行一个有边界的阶段。这样同事使用同一个工作台时得到相同的规范，而不依赖某个人在交互式 Pi 中手动启动技能。

首批团队规范在 `backend/trellis_bundle/`。其中 `library/` 从现有 `.trellis/spec/` 精选了跨层思考、前端类型与组件、后端错误处理四篇原始规范；阶段系统上下文只列出相关文档路径，Pi 按需从只读镜像读取。个人工作日志、机器配置、环境地址、SOP 和历史工单不会进入镜像。新增规则应先由团队评审，再修改 bundle 并运行测试、重建镜像。

## 一次任务的交接

1. Runner 克隆 UI 已确认的仓库并锁定目标 commit。`prepare_trellis_context` 在该 attempt 的 `/workspace/.trellis/tasks/bugfix/` 写入 `task.json`、`prd.md`、`implement.md`、`implement.jsonl` 和 `check.jsonl`。三个角色的系统上下文由只读镜像生成、保存在协调器内存中，启动 Pi 时作为独立参数传入，不能由前一阶段修改。`prd.md` 保存工单快照，属于不可信数据。
2. **定位会话**只读仓库，输出 `diagnosis.json`（根因、证据、方案、涉及仓库）。服务端核对所有仓库仍干净；阶段不合格就停止。
3. **实施会话**读取诊断，在允许的仓库中修改代码，输出 `manifest.json` 和每仓确定性的修前/修后复现命令。服务端在原始 commit 上执行命令，确认失败后冻结候选 Git 树。
4. **独立验证会话**不继承实施对话，只读候选和修前证据，输出 `verification.json`。服务端在冻结树上运行同一命令，要求通过且 Git 树未被验证者修改。
5. 候选进入工作台供另一名成员审核；只有审核后，独立交付器才能推分支和创建 PR。

诊断、实施和验证的 JSON 结果另存到任务目录的 `research/`，形成可检查的工作记忆；每次 attempt 使用独立目录，不把上一次尝试的推断当成新尝试的事实。

这三个 Pi 进程是由 Runner 显式调度的独立角色。每个进程用 Pi 官方 `--append-system-prompt` 接收自己的 Trellis 上下文，并用 `--no-extensions --no-skills` 排除个人全局扩展。规范库保存在只读镜像的 `/app/trellis_bundle/`，不放在 Pi 可写的 `/workspace`。`/workspace` 只包含本次 attempt 的仓库和工件。Pi 的交互式 Trellis 扩展仍适合人工开发，但服务端采用显式阶段调度，避免模型自行决定是否调用子工具。

## 团队维护

- `workflow.md` 定义所有人共用的阶段和交接门槛。
- `spec/core.md` 是所有仓库都会收到的规则；`backend.md`、`frontend.md` 按已选仓库注入。目标仓库内已提交的 `AGENTS.md` 和规范仍须遵循。
- 一次真实 Bug 的规则缺口先写入任务回顾，经团队审查后再写入 bundle。不要把一次故障的偶然现象直接升级为全局规则。
- 观察指标：定位证据是否具体、修前失败是否对应工单、修后是否运行同一命令、独立验证是否发现问题、审核人是否需要补充信息。用这些结果决定后续要迁移的 spec，而不是一次复制整个个人知识库。

## 当前验收边界

本接入已有单元测试、模拟 Pi 流程验证及 42 机真实模型三阶段合成 Bug 烟测。飞书和 GitHub 凭据配置后，仍须用未解决 Bug 做全链路验收。当前版本未提供从工作台编辑或审批团队 spec 的 UI。
