# 任务生命周期与执行协议

## 1. 协议范围

本文只定义调度、租约、进程、阶段提交、取消和恢复协议。Agent 的业务阶段与用户交互见 [02-agent-workflow流程](02-agent-workflow流程.md)，信息规则见 [05-信息诊断 Agent 规则](05-信息诊断agent-规则.md)，数据与 API 见 [03-数据模型与外部集成](03-数据模型与外部集成.md)。

## 2. 任务与执行尝试

Job 保存业务任务，workflow.stage 保存当前阶段，attempt 保存一次领取后的隔离执行。一次 Job 可以经历多个阶段与多个 attempt。等待用户答复是持久化状态，不需要挂着模型进程等待。

下图只表达执行生命周期，不展开 Agent 业务流程：

~~~mermaid
stateDiagram-v2
  [*] --> queued
  queued --> running: 原子领取与创建 attempt
  running --> queued: 阶段结果通过，下一阶段可调度
  running --> needs_input: 输入或取证不足
  running --> awaiting_business_confirmation: 等待用户选择
  running --> awaiting_prd_input: 等待 PRD 答复
  needs_input --> queued: 补充或刷新输入
  awaiting_business_confirmation --> queued: 确认或要求调整
  awaiting_prd_input --> queued: 答复后重新收敛
  running --> failed: 超时或执行错误
  queued --> cancelled: 取消
  running --> cancelled: 取消
  failed --> queued: 重试并重置门槛
  cancelled --> queued: 重试并重置门槛
  running --> review_ready: 验证后的候选冻结
  review_ready --> delivery_wip: 已审核，逐仓协调
  review_ready --> delivered: 交付成功
  delivery_wip --> delivered: 交付恢复成功
~~~

其他执行结果包括 unreproduced、diagnosis_only；两者不能作为已修复候选交付。wip_incomplete 表示多仓 PR 转换和回退未完全成功，需要核对远端交付状态。

## 3. 阶段领取与提交

Store 在 BEGIN IMMEDIATE 事务中领取 queued 或租约过期 running 任务，提升 lease_epoch、创建 attempt 并登记 lease_owner。租约为 60 秒，Worker 每约 15 秒续租；续租覆盖代码准备和 Runner 运行期间。

阶段结果只接受当前 running Job、相同 epoch、相同 workflow.stage 和有效 snapshot_hash。报告经过结构验证后保存，推进 revision、结束当前 attempt、清理租约，并转入下一 queued 或等待用户状态。旧进程即使继续生成文件，也不能用旧 epoch 写回权威状态。

用户操作使用 expectedRevision 校验同版输入。补充、源刷新、业务范围调整和 PRD 答复会取消旧批准的推进效力；用户未答复不自动恢复任务。

来源：[workflow.py](../../backend/app/workflow.py)、[store.py](../../backend/app/store.py)。

## 4. Runner 分工与产物

规划阶段使用 stage_runner，实施阶段使用 task_runner。每次 attempt 使用独立 Docker Runner，根文件系统只读，attempt 目录挂载为 /workspace；容器限制 CPU、内存、PID 并移除 capabilities。

| 执行路径 | 输入 | 产物与机械门槛 |
| --- | --- | --- |
| 信息诊断 | 独立快照、用户补充 | 必需字段先机械检查，再验证 complete 报告；不足转 needs_input |
| 根因查询 | 已通过的信息、74 日志、分析仓库 | confirmed 结论须包含日志、代码证据及一至三项业务变化 |
| PRD 编写 | 根因报告、用户确认、反馈记录 | 报告 content 非空，业务确认绑定根因哈希；未收敛等待用户 |
| 独立 PRD 复核 | 同版 PRD 及 hash | converged=true 且 prd_hash 匹配才许可实施 |
| 实施验证 | 已通过的 PRD、根因、代码基线 | 创建修改 worktree，实施清单、修前/修后证据、独立验证和冻结候选 |

规划 Runner 写 stage-report.json，并以 result.json 返回阶段报告；协调器校验后保存到 workflow。stage_runner 不将输入快照改名为 PRD，规划报告中的 content 是 PRD 文本。实施准备只使用已批准 PRD 写入 .trellis/tasks/bugfix/prd.md。

根因阶段可准备只读分析仓库；修改工作区只在 ready_for_implementation 通过后创建。工作区采用 Git worktree 独立目录，不调用开发者聊天里的技能名称作为远端执行协议。分析范围是两仓，候选允许是实际发生修改的仓库子集。

来源：[stage_runner.py](../../backend/app/stage_runner.py)、[task_runner.py](../../backend/app/task_runner.py)、[trellis_context.py](../../backend/app/trellis_context.py)。

## 5. Pi RPC 生命周期

每阶段新建 Pi RPC 会话。可信规则通过受控系统上下文传入，快照、日志、补充和仓库内容作为不可信任务数据。私钥和发布凭据不交给模型。

prompt 通过 stdin 发送带 request ID 的 JSONL 命令。对应 response.success=true 表示请求接受；只有随后收到 agent_settled 才表示该次模型请求完成。disposition=handled 不等于 settled；rpc_eof、rpc_error、拒绝 response 和 deadline 都属于显式失败。

阶段结束还需要文件存在、不是符号链接、JSON 结构合法和业务门槛有效。产物文件存在不能代替 RPC 完成，RPC 完成也不能代替内容校验。

Pi prompt 默认超时 300 秒；Worker 传入同样的阶段上限。收尾总等待限制为 3 秒：发送 abort 后等待进程 0.25 秒，必要时 kill；stdin.wait_closed 最多等待 0.5 秒；最后取消读取任务。stderr 保存限长尾部，错误输出前脱敏 token、secret、API key、password 和 Authorization。

来源：[pi_rpc.py](../../backend/app/pi_rpc.py)。单阶段时限不是整个多阶段 Job 的总时限，等待用户的时间也不计为模型运行时间。

## 6. 外部调用与取消

| 边界 | 时限或约束 |
| --- | --- |
| 仓库 clone/fetch/独立复制 | Git 命令上限 300 秒；缓存初次 depth 40，后续 fetch 更新 |
| SSH74 日志 | 连接超时 10 秒，整体命令超时 60 秒，固定主机和受控查询程序 |
| Pi 单次请求 | 默认 300 秒 |
| Pi 会话收尾 | 总上限 3 秒 |
| 修前/修后命令 | 默认 300 秒，超时记为 exit 124 |
| Docker volume inspect | 10 秒 |
| Docker stop | 指令等待上限 15 秒，停止宽限 2 秒 |

取消使 Job 进入 cancelled，后续带旧 epoch 的阶段提交不能生效。Runner 监控在发现租约失效后停止容器。同步代码/日志准备命令通过各自时限约束，不把 API 返回“已取消”解释为所有外部子进程已经立即消失。

## 7. 重试与版本失效

发起人可重试 failed、cancelled、unreproduced、diagnosis_only。重试保留历史事件、attempt 和输入记录，清空当前错误、候选和租约，提升 epoch，并重置到 information；根因、业务确认、PRD 与独立审查必须重新通过，不从旧文件推断可以继续实施。

重新读取工单是独立操作：后端重新访问飞书，保存 source_snapshot_version 和快照版本，更新源标识，再重新诊断。提交补充信息不会伪造飞书源标识；偶现 trace-id 必须存在于工单源数据。

PRD 答复回到 prd，清空独立审查与实施许可；调整业务范围回到根因阶段；拒绝业务变更停止任务。新版本不能复用旧版审批。

## 8. 冻结候选与交付

实施会话只能修改工作区，输出 manifest 和实际修改仓库集合。修前在目标 SHA 的基线执行复现命令；修后在冻结候选的干净 worktree 执行相同命令。独立验证会话不能修改候选树。缺依赖等环境错误不能被当成业务复现成功。

Worker 校验仓库集合、路径、目标分支、目标 SHA、tree_id 及 PRD 双审许可后保存 candidate，转入 review_ready。审核拒绝发起人自审；审核绑定 candidate ID 与逐仓 tree、目标分支、基线 SHA。

交付前重新核对远端目标 SHA。先创建或协调逐仓 Draft PR，再将整组转为可审核；中途失败保留 delivery_wip，采用确定性分支与远端查询避免重复创建。目标分支移动时不能自动继承旧审核，需要重新验证候选。

来源：[review.py](../../backend/app/review.py)、[delivery.py](../../backend/app/delivery.py)、[delivery_worker.py](../../backend/app/delivery_worker.py)。
