# 总体系统设计

## 1. 系统目标与边界

Bug 修复工作台将飞书工单、日志证据、代码修改和人工决策组织为可追溯任务，交付经验证和审核的 GitHub PR。

业务范围为 voyager_server 与 operations-dashboard。192.168.2.42 承载工作台，192.168.2.74 提供取证环境。飞书项目提供缺陷输入，GitHub 承载代码与 PR。合并、发布和最终业务验收由团队完成。

## 2. 大组件及职责

| 大组件 | 核心职责 | 责任边界 |
| --- | --- | --- |
| 前端工作台 | 展示任务、证据与文档，收集用户补充、选择和审核 | 不自行判定阶段通过 |
| 后端 API | 输入校验、身份认证、任务查询及操作入口 | 不在请求内执行长期模型任务 |
| 流程协调服务 | 校验门槛、调度、租约、取消及恢复 | Agent 结论不能自行推进权威状态 |
| Agent 执行服务 | 受控分析、规划、修复与验证 | 不掌握对外发布决定权 |
| 外部集成适配层 | 访问飞书、取证环境、模型和 GitHub | 不同系统使用独立身份和能力授权 |
| 持久化存储 | 保存状态、快照、确认、文档与证据 | 明确版本关联，保留事实来源 |
| 工作区管理服务 | 维护缓存、固定代码基线、创建隔离工作区 | 共享缓存与任务修改隔离 |
| PR 交付服务 | 校验审批绑定并协调逐仓发布与恢复 | 不发布未获有效审批的候选 |

组件之间的访问关系见 [08-组件关系](08-组件关系.md)。本文件不展开 Agent 阶段和执行顺序。

## 3. 系统边界

### 用户决策边界

用户决定业务行为与审核结果，系统保存决定及其内容版本。未回答不视为同意；前端交互与后端权限校验一致。

### 控制与执行边界

协调服务管理权威状态，执行服务仅在授权范围内生成产物。进程存活、心跳、文件生成和阶段成功是不同事实，不能相互替代。

### 数据与规则边界

飞书字段、评论和仓库文本属于来源数据；系统规则、规范索引、工具授权与用户确认独立管理。原始快照与收敛后的 PRD 是不同对象。

### 工作区与发布边界

代码分析范围不等于实际修改范围。修改工作区按任务隔离，候选绑定基线与冻结树，发布能力由交付服务持有。

## 4. 运行与持久化

交互请求和长期执行解耦。状态数据库与产物存储跨重启保留，临时执行环境按尝试隔离。仓库首次浅克隆，后续 fetch 更新缓存，任务工作区不共享可变代码。

各外部依赖分别检查身份、权限与连通性。执行具有截止时间、进展记录、失败原因和取消处理；恢复时重新检查版本及批准的有效性，阻止旧执行覆盖新结果。
