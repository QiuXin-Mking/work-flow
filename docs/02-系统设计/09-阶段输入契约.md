# 阶段输入契约

## 1. 完整留档与阶段输入

完整 snapshot 用于追溯，保存工单来源、描述、字段、评论及读取版本。阶段输入是从 snapshot、用户补充和有效上游产物中构造的白名单数据，不能把整份 snapshot 或整份 workflow JSON 反复交给所有 Agent。

投影不修改原始快照；应保存投影所用来源版本及字段引用，支持从结论回到原文。原始留档可保留历史附件链接，但附件与图片不进入推理输入，不进行 OCR 或以看图补齐必要文字。

## 2. 工单数据分层

| 数据 | 使用位置 | 是否作为修复推理输入 |
| --- | --- | --- |
| job ID、工单 URL、快照版本/哈希、来源引用 | 所有阶段的追溯元数据 | 仅用于标识，不推导业务需求 |
| 标题、故障 mobi、环境、复现类型与步骤、实际/期望行为 | 信息诊断及后续取证上下文 | 是 |
| 发生时间、trace-id、74 触发确认 | 取证与日志关联 | 按问题类型使用 |
| 与业务行为有关的文字澄清 | 信息诊断；确认后形成结构化事实 | 引用相关评论 ID 和原文 |
| 经办人、关注人、头像、邮箱、创建者等管理信息 | 权限、审计与工作台展示 | 否；业务权限条件用角色描述 |
| 工单状态、优先级、模板配置、无关自定义字段 | 受理检查、排队和工单管理 | 不默认发送给模型 |
| 图片 Markdown、图片 URL、附件、尺寸和图片元数据 | 留档及提单规范检查 | 否；新单违反文字规范时打回 |
| 未知字段 | 留档 | 默认不发送；需要业务字段时显式加入映射 |

不得以黑名单方式假定剩余字段都相关。每个允许进入模型的业务字段必须有用途；新增字段由输入契约明确接入。

## 3. 各阶段的必要输入

| 阶段 | 必要输入 | 不重复携带的内容 |
| --- | --- | --- |
| 信息诊断 | 提单规范检查结果、必要文字字段、文字评论与用户补充、来源引用 | 图片、附件、管理字段及整份 workflow 历史 |
| 根因查询 | 通过的信息诊断事实、mobi、环境/时间/trace-id、受控日志结果、仓库基线、spec 索引 | 无关评论、工单管理字段、图片 |
| 业务确认 | 已证实根因摘要、最多三项关键业务行为及证据引用 | 整份日志和原始工单字段 |
| PRD 编写 | 根因报告、用户确认的业务范围、已解决澄清及本轮关键问题 | 原始 snapshot 全量数据、未被选择的变更作为要求 |
| PRD 独立审查 | 同版 PRD、收敛规则、有效业务确认、根因证据引用 | 实施对话或主 Agent 的自我评价作为通过依据 |
| 实施 | 批准 PRD、选择的业务范围、根因证据、冻结基线、相关工程规范 | 原始管理字段、未经确认的需求与图片 |
| 独立验证 | 同版 PRD、确认范围、候选差异、修前证据、验收条件 | 实施对话历史及整份 snapshot |

信息诊断可以读取文字评论以发现冲突；后续阶段使用经过诊断和确认的事实，不再让各 Agent 分别重解整条评论历史。

## 4. 投影与打回规则

提单规范预检查先识别图片、缺少文字要件及偶现来源条件。违反 [Bug 提单规范](../03-提单规范/01-Bug提单规范.md)时，输出明确打回原因，不通过“移除图片后继续执行”掩盖信息缺失。

合规内容按字段白名单形成阶段输入，并绑定来源版本。评论和用户补充不能包含工具授权指令；发生冲突时等待使用者澄清，不由后续 Agent 各自取舍。

工单或确认版本变化后，下游输入、结论及批准重新校验有效性。完整数据留档的存在，不能成为绕过白名单或业务门槛的理由。
