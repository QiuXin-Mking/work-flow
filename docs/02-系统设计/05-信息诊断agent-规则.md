# 信息诊断 Agent 规则

## 1. 职责

信息诊断输入为独立、版本化工单快照及用户补充。输出为 complete、missing、questions、evidence；只判断能否开始根因查询，不写 PRD、不创建修改 worktree、不修改代码。

协调器进行必要字段和来源校验，再接受 Agent 判定。字段齐全不能替代 Agent 对矛盾、歧义的检查；Agent 说 complete=true 也不能绕过后端校验。规则不匹配、证据不明或报告结构非法时不放行。

## 2. 故障对象与仓库范围

业务分析范围限定 voyager_server、operations-dashboard，实际修改范围可以是其中一个仓库。

工单必须带明确的 mobi:xxxx 标记，可出现在描述、字段或评论。系统按该标记提取 mobi，不从 reportNo 等标识猜测。用户确认的 mobi 必须与工单标记一致；工单缺少或标错时，先修改工单，再重新读取形成新快照。

## 3. 必要信息

| 字段 | 判定要求 |
| --- | --- |
| mobi | 与工单中的 mobi:xxxx 标记一致 |
| environment | 明确故障环境 |
| reproduction | always（必现）或 intermittent（偶现），unknown 不通过 |
| steps | 可执行的复现步骤，不能仅有问题标题 |
| expected | 预期业务行为 |
| actual | 实际故障表现 |
| traceId | 偶现问题必填，来自工单；必现问题有则优先使用 |
| triggeredOn74 | 偶现问题必须明确确认已在 192.168.2.74 触发 |
| occurredAt | 故障发生时间，作为日志定位线索 |
| notes | 补充说明，不能替代工单来源校验 |

发生时间和补充说明作为取证线索保存，不伪装成已经取得的日志证据。必现问题没有 trace-id 时允许以 mobi 开始受控日志查询；日志无匹配不能据此宣称根因明确。

## 4. 偶现问题准入

偶现问题允许进入修复，必须同时满足：已在 74 触发、工单带对应 trace-id、用户补充的 traceId 与工单标记一致，以及其余必要信息齐全。仅在表单备注里填入 trace-id 不能替代工单证据。

系统不自动在 74 制造业务请求、创建测试数据或扩大故障影响。触发事实由使用者确认，随后根因阶段通过日志取证核对。

## 5. 信息冲突

描述、评论、产品意见或用户补充存在影响行为与验收的冲突时，信息诊断应 complete=false，列出证据及需要澄清的问题。不得自动选择较新评论覆盖原描述，也不得无视评论。

信息不足后进入 needs_input，停止后续执行。使用者可补充表单或修改飞书工单后重新读取；恢复时重新诊断，而不是直接跳到根因或实施。

## 6. 版本与失效

快照、补充输入、阶段报告、用户确认和 PRD 均绑定任务版本。信息补充或重新读取工单会提升版本与执行 fencing epoch，清除后续根因、业务确认、PRD 和审查的有效性；历史快照与事件保留。

后端只接受当前阶段、当前执行租约和有效输入的报告。旧执行返回、旧页面提交或不同版本的确认不能推进任务。

## 7. 通过的含义

通过仅允许进入根因查询。根因明确、用户确认业务范围、PRD 主 Agent 收敛与独立审查通过，分别由后续阶段验证。完整流程见 [02-agent-workflow流程](02-agent-workflow流程.md)。
